# opencode adapter - design

Date: 2026-08-29
Status: implemented
Builds on: docs/superpowers/specs/2026-08-28-events-and-recall-design.md

## Purpose

The events-and-recall design names three harnesses - Claude Code, Cursor,
opencode - and ships only the first. This design covers opencode: the second
adapter, and the first one that is not a shell hook.

It matters more than "one more integration". The Claude Code adapter and the
events pipeline underneath it were shaped by an argument about what a harness
can be assumed to provide - no transcript, no reliable session end, extraction
triggered by a clock rather than a hook. opencode is the harness that argument
was written against. Building it is what proves the pipeline is actually
harness-neutral rather than Claude Code with a seam drawn around it.

## What opencode gives us

Verified against `@opencode-ai/plugin` 1.3.5, installed at
`~/.opencode/node_modules/@opencode-ai/plugin/dist/index.d.ts`, with the
`opencode` binary on PATH.

A plugin is an ES module exporting `server`, a function of
`(input: PluginInput, options?: PluginOptions) => Promise<Hooks>`. `PluginInput`
carries `client`, `project`, `directory`, `worktree`, `serverUrl`, and `$` - a
Bun shell. The three hooks this design uses:

| Hook | Signature (abridged) | Used for |
|---|---|---|
| `tool.execute.after` | `({tool, sessionID, callID, args}, {title, output, metadata})` | recording tool-call events |
| `chat.message` | `({sessionID, agent?, model?, messageID?}, {message, parts})` | recording the user turn |
| `experimental.chat.system.transform` | `({sessionID?, model}, {system: string[]})` | injecting the knowledge base |

Three facts about opencode shape everything below:

1. **There is no session-start hook.** The only injection point is
   `experimental.chat.system.transform`, which fires on *every* message.
2. **There is no session-end hook.** Extraction stays idle-triggered, which is
   what the events pipeline was already built for. Nothing here changes it.
3. **The plugin runs in-process.** There is no harness-imposed timeout to
   inherit, unlike the 5s and 10s the Claude Code adapter gets for free.

`experimental.session.compacting` also exists - opencode tells a plugin that a
session is about to be compacted, which is the closest thing it has to an
end-of-session signal and is conceptually near remem's handoff trigger.
**Deliberately out of scope here.** It is recorded so it is not rediscovered as
a novelty later; idleness remains the only extraction trigger, for the reason
the events-and-recall design gives - a trigger all three harnesses share.

## Requirements

- `remem install opencode` registers event recording and knowledge base
  injection, globally or per project.
- Recorded events reach `remem record event` in the shape `services/record.py`
  already consumes, behind the existing per-project opt-in.
- The knowledge base block is injected once per session.
- A failure anywhere in the plugin is invisible to the user and never delays a
  turn beyond a bounded timeout.
- A test fails if the plugin ever subscribes to a hook opencode does not emit.

## Design

### What ships, and where

A new adapter package `src/remem/agents/opencode/`, mirroring
`agents/claude_code/`:

```
src/remem/agents/opencode/
  __init__.py
  adapter.py     # the Agent implementation, registered under remem.agents
  plugin.js      # the marshaller, shipped as package data
  install.py     # writes plugin.js into opencode's plugin directory
  hooks.py       # the vendored hook-name list (see "The contract test")
```

`remem install opencode` writes `plugin.js` verbatim into opencode's
plugin directory: `~/.config/opencode/plugin/` for a global install,
`.opencode/plugin/` for a per-project one. The directory is the registration -
opencode loads what it finds there, so **install never touches the user's
`config.json`**. That is worth stating as a property rather than an
implementation detail: there is no user config file to back up, to merge, or to
corrupt, which is the failure mode the `remem config` design spends most of its
safety budget on.

The file is overwritten unconditionally, with no version marker. remem owns it.
A `// generated by remem - do not edit` header says so, and the install reports
the path it wrote - the same courtesy `remem config` extends for its backups.
The rejected alternative was a version marker that install reads to decide
whether to rewrite; it buys nothing when the file is machine-owned and nobody
is expected to have edited it.

### The plugin file

`plugin.js` **imports nothing**. `$` arrives on `PluginInput`, so shelling out
needs no runtime dependency, and `@opencode-ai/plugin` is a types-only
development dependency used by the contract test and never at runtime. This is
the core of the approach: the JS is a dumb marshaller, and every policy
decision stays in Python where the other frontends can share it.

It exports `server`, destructures `{$, directory, worktree}`, and returns the
three hooks:

- **`tool.execute.after`** shapes its two argument objects into JSON and pipes
  it to `remem record event` on stdin.
- **`chat.message`** does the same for the user turn.
- **`experimental.chat.system.transform`** consults a module-level
  `Set` of session IDs. On a session it has not seen, it shells out for the
  knowledge base block and pushes the result onto `output.system`; on any later
  message in that session it returns immediately.

The `Set` is the one piece of policy the JS holds, and it is there under
protest: per-process state has nowhere else to live. It is called out here so
the next reader knows it is a deliberate exception to "all policy in Python"
and not a leak.

**Injection is once per session**, matching the Claude Code adapter's
SessionStart semantics. The consequence is explicit: a memory written mid
session is not visible until the next session. The alternative - re-injecting a
freshly read block every turn, which opencode's hook shape actually permits and
Claude Code's does not - was considered and rejected for this change. It trades
an unmeasured per-turn token and database cost for a freshness nobody has asked
for yet. If it is ever wanted, the plugin change is one line; the reason to
wait is that the cost should be measured first.

Every shell-out is wrapped in a timeout and a `try`/`catch` that swallows
everything. The timeouts are **5s for event recording and 10s for the knowledge
base block**, matching the values the Claude Code adapter's PostToolUse and
SessionStart hooks are registered with, so the two adapters fail on the same
schedule. **This is the fail-soft contract, and the plugin has to implement it
rather than inherit it.** The Claude Code hooks exit 0 and stay
silent partly by discipline and partly because the harness kills them at 5s or
10s. Nothing kills a hung in-process plugin hook, so an unbounded `remem` call
here does not degrade the session, it stops it.

### Injection has to become harness-neutral first

Recording already is: `remem record event --agent <name>` resolves an adapter
through the registry and probes `event()` with `getattr`, so a new harness needs
no CLI work at all. **Injection is not.** `remem hook session-start` reads a
Claude Code payload, is hard-wired to `ClaudeCodeAdapter`, and builds the context
block inside `hook.py` - which is a frontend, holding a decision the layering
says belongs in a service. A second harness can therefore record events today
but cannot be told anything.

So this change also:

- moves the block-building into `services/context.py`, with the handoff pointer
  that goes with it, and
- adds `remem hook context --agent <name>`, the neutral half of what
  SessionStart does, which reads whatever payload the harness has and turns it
  into a project through the adapter's `identity()` - a required Protocol
  method, so every adapter already has one.

`session_start` becomes a thin wrapper over the same service the opencode plugin
reaches through the CLI. This is not scope creep bolted onto an adapter: without
it the plugin's third hook has nothing to call, and the alternative - a second
opencode-specific block builder - would be the duplication the seam exists to
prevent.

### The Python side

`OpenCodeAdapter.event()` parses the opencode payload into the shape
`services/record.py` already consumes. The adapter parses, the service decides -
the same split as `ClaudeCodeAdapter.event()`, and `event()` remains an optional
capability probed with `getattr`. The per-project opt-in gate is untouched and
remains the entire safety story.

The adapter implements **neither `env_settings()` nor `settings_path()`**. They
are optional capabilities that go together, and CLAUDE.md is explicit that an
adapter with only one of them is worse than an adapter with neither. remem has
no curated table of opencode environment variables, so `remem config` correctly
reports "no settable env vars" for this agent, and no fallback to another
agent's file can occur.

Project resolution stays in Python, from the working directory the plugin
passes, so worktrees and subdirectories file under the repository root exactly
as every other write path does.

### The contract test

The events-and-recall design asks for a test asserting each adapter subscribes
only to events its harness actually emits - the regression guard against the
silent dead loop claude-mem shipped when it bound to event names opencode does
not emit.

The naive form of that test reads
`~/.opencode/node_modules/@opencode-ai/plugin/dist/index.d.ts` and `pytest.skip`s
when it is absent. **That is unacceptable here**, and for a reason this project
has already paid for: a suite that reports success while silently not running
the check is the exact failure the `db` markers taught us to distrust. A guard
that skips on CI is not a guard.

So the check is split in two:

1. **A vendored hook-name list** in `agents/opencode/hooks.py` - the names from
   `Hooks` in 1.3.5, checked into the repository with the version they came
   from. The contract test asserts the hooks `plugin.js` subscribes to are a
   subset of that list. **This test always runs**, everywhere, with no
   dependency on node_modules, and it is the one that guards the plugin.
2. **A freshness test**, marked `opencode`, that reads the installed types and
   asserts the vendored list still matches. It skips where opencode is not
   installed, and that is fine, because what it guards is our copy of an
   external fact rather than the correctness of the plugin.

The two tests answer different questions - "does the plugin subscribe to
something we believe is not real" and "is what we believe still true" - and
conflating them is what produces a guard that evaporates on CI.

### Testing

- `event()` parsing, against payloads captured from a real opencode session.
- Install: writes to a tmp directory, asserts the file lands in the right place
  and that a second install overwrites a modified copy.
- The contract test above, both halves.
- End to end: `opencode` is on PATH and the plugin types are installed at 1.3.5,
  so unlike Cursor this adapter can be exercised for real - opt a scratch
  project in, run a session, assert events land and the block is injected once.

## Out of scope

- The Cursor adapter. It is the remaining third of the events-and-recall
  design and gets its own plan.
- `experimental.session.compacting`, per the reasoning above.
- Re-injecting the knowledge base per turn.
- Any change to extraction, the opt-in gate, or the events schema. This design
  adds a producer; it changes nothing downstream of `remem record event`.
